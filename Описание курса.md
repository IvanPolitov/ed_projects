## Pre-flight (перед проектом 1) `➕`

*Добавлено, чтобы не входить в asyncio/SQLAlchemy async с нуля. Полдня-день,
не отдельный репозиторий, а модуль внутри будущего Job Runner.*

- [ ] `@retry(times=3, delay=1, exceptions=(ConnectionError,))` — с задержкой, логирует каждую попытку
- [ ] `@timeit` — логирует время через `logging`, не `print`
- [ ] Свой генератор/итератор (пригодится в Project 1 для последовательной выдачи задач)

**Инструменты:** `functools`, `logging`, `time`

**Зачем:** `@retry` и генератор пишутся один раз здесь и потом переиспользуются в Async Job Runner и Async Data Aggregator — не нужно изобретать retry-логику на лету посреди проекта с уже большим scope.

# Проект 1. Async Job Runner

## Цель

Создать сервис фонового выполнения пользовательских задач. Главная цель —
разобраться в `asyncio`, конкурентности, HTTP и жизненном цикле фоновой
задачи.

## Что должно быть

REST API:

- `POST /jobs` — создать задачу;
- `GET /jobs/{id}` — получить состояние и результат;
- `GET /jobs` — список задач с пагинацией и фильтрацией;
- `POST /jobs/{id}/cancel` — отменить задачу.

Статусы: `PENDING → RUNNING → COMPLETED / FAILED / CANCELLED`

Типы задач:

1. `sleep` — ожидание N секунд;
2. `http_request` — HTTP-запрос;
3. `url_check` — проверка доступности URL и времени ответа;
4. `batch_http` — конкурентная обработка списка URL.

Реализовать:

- `asyncio.Queue`;
- несколько worker'ов;
- ограничение concurrency;
- timeout;
- cancellation;
- retry (используй декоратор из Pre-flight);
- graceful shutdown;
- сохранение состояния задач в PostgreSQL;
- сравнение sync / threads / processes / asyncio на отдельном benchmark;
- небольшое отдельное упражнение TCP client/server;
- генератор/итератор для последовательной выдачи задач;
- unit и integration tests.

## Использовать

FastAPI · asyncio · aiohttp или httpx · PostgreSQL · SQLAlchemy 2.x async ·
asyncpg · Alembic · Pydantic · pytest · Docker Compose · Ruff · mypy

**Не использовать пока:** Celery, RabbitMQ, Redis.

# Проект 2. Personal Finance API

## Цель

Backend для учёта личных финансов, глубокая практика PostgreSQL, ORM, raw
SQL и оптимизации запросов.

## Что должно быть

Сущности: User, Account, Category, Transaction, Budget, RecurringTransaction

Возможности:

- создание счетов;
- доходы и расходы;
- категории;
- переводы между счетами;
- месячные бюджеты;
- фильтрация операций;
- пагинация;
- статистика по месяцам;
- статистика по категориям;
- cash flow;
- сравнение расходов с предыдущим месяцем.

Обязательно:

- часть запросов через SQLAlchemy ORM;
- сложную аналитику написать raw SQL;
- CTE;
- aggregation;
- window functions;
- транзакции;
- constraints;
- индексы;
- `EXPLAIN ANALYZE`;
- намеренно создать N+1, обнаружить и исправить;
- кеширование тяжёлой статистики в Redis;
- миграции;
- тесты БД.

**`➕` Права доступа (DCL).** Отдельным скриптом (не через ORM) создать в
Postgres роли `readonly` и `readwrite`, раздать права через `GRANT`/`REVOKE`
на таблицы проекта, продемонстрировать разницу — под `readonly` запрос на
`UPDATE` должен падать. Тема прав доступа к БД регулярно всплывает на
собеседованиях мидла, а в исходном курсе её не было вообще.

## Использовать

FastAPI · PostgreSQL · SQLAlchemy 2.x · asyncpg · Raw SQL · Alembic · Redis ·
pytest · Docker Compose

# Проект 4. Booking System

## Цель

Сервис бронирования ресурсов, правильная работа с транзакциями,
блокировками и race conditions.

Пример предметной области: бронирование переговорных комнат или рабочих
мест.

## Что должно быть

Сущности: User, Room, Booking, Schedule

API:

- просмотр комнат;
- просмотр свободных интервалов;
- создание бронирования;
- отмена бронирования;
- просмотр своих бронирований.

**Главное требование:** две конкурентные операции не должны иметь возможность
забронировать один ресурс на пересекающееся время.

Провести эксперимент:

- запустить десятки/сотни конкурентных запросов на один ресурс;
- доказать тестом, что данные остаются корректными.

Изучить и применить: transactions, isolation levels, row locks, PostgreSQL
constraints, race conditions, deadlocks, retry транзакций, idempotency.

## Использовать

FastAPI · asyncio · PostgreSQL · SQLAlchemy · Raw SQL · Alembic · pytest ·
Docker Compose

# Проект 5. Async Data Aggregator

## Цель

Сервис, агрегирующий данные из нескольких внешних источников, глубокое
изучение aiohttp и сетевого программирования.

## Что должно быть

Сервис получает запрос и одновременно обращается к нескольким внешним API.

Например: `GET /products/{id}/prices` должен запросить несколько
поставщиков и вернуть объединённый результат.

Реализовать: concurrent HTTP requests, connection pooling, timeout, retry с
backoff, semaphore, rate limiting, circuit breaker, обработку частичного
отказа, кеширование, нормализацию разных форматов JSON, генераторы для
потоковой обработки больших наборов данных.

Сценарий: Provider A отвечает за 100 ms, Provider B — за 300 ms, Provider C
зависает. API не должен ждать Provider C бесконечно и должен уметь вернуть
частичный результат.

Дополнительное упражнение: получить HTML-страницу, извлечь несколько полей
через BeautifulSoup, преобразовать их в структурированный JSON.

## Использовать

FastAPI · aiohttp · asyncio · PostgreSQL · Redis · SQLAlchemy · BeautifulSoup
(доп. упражнение) · pytest · Docker Compose

# Проект 6. Notification Service

## Цель

Отдельный сервис уведомлений, брокеры сообщений, фоновые задачи и
event-driven подход.

## Что должно быть

API принимает запрос: `POST /notifications`

Типы уведомлений: email, webhook, условный internal notification.

Архитектура: `API → RabbitMQ → Worker → Provider`

Реализовать: асинхронную постановку сообщения в очередь, background workers,
retry, exponential backoff, scheduled notifications, историю отправок,
шаблоны сообщений, idempotency, rate limiting, dead-letter обработку
неуспешных сообщений, защиту от повторной отправки одного уведомления.

API должен быстро возвращать `202 Accepted`, не ожидая фактической отправки.

## Использовать

FastAPI · RabbitMQ · Celery · Redis · PostgreSQL · SQLAlchemy · Docker
Compose · pytest

# Проект 7. Production Deployment

## Цель

Взять один из предыдущих сервисов и довести его до состояния, близкого к
production.

## Что должно быть

**`➕` Шаг 0 — вручную, без Docker.** Прежде чем контейнеризировать,
задеплой тот же сервис руками на VPS/VM: uWSGI (или Gunicorn/Uvicorn для
FastAPI) как application server, nginx как reverse proxy + отдача статики,
конфиг через `.ini`/systemd-unit, не inline-командами. Смысл шага — увидеть
своими руками, что именно потом абстрагирует Docker, а не воспринимать
контейнеризацию как чёрный ящик.

Контейнеры: API, worker (если нужен), PostgreSQL, Redis, RabbitMQ (если
нужен), Nginx.

Настроить: Dockerfile, multi-stage build, Docker Compose, volumes, networks,
healthcheck, environment variables, secrets, Nginx reverse proxy, HTTPS,
graceful shutdown, structured logging.

**`➕` HTTPS — пошагово.** Привязать домен (можно бесплатный поддомен,
например duckdns.org) через A-запись. Certbot выпускает сертификат Let's
Encrypt и настраивает автопродление (`certbot renew --dry-run` — проверить).
nginx принудительно редиректит HTTP → HTTPS, прямой HTTP-доступ закрыт.
Итог проверяется через SSL Labs (рейтинг A/A-).

**`➕` Bash-автоматизация.**
- `deploy.sh`: git pull → build → up -d → health-check по `/health` → откат при неудаче; идемпотентен, `set -euo pipefail`, логирует каждый шаг
- `backup.sh`: `pg_dump` с датой в имени, ротация (хранить последние 7 копий), запуск через cron

CI/CD: `push / pull request → lint → type check → tests → build Docker image`

Добавить: Ruff, mypy, pytest, GitHub Actions.

Практика Linux: процессы, signals, permissions, environment variables,
networking, `curl`, `ps`, `top`, `grep`, `journalctl`, базовая диагностика
работающего сервиса.

## Использовать

Docker · Docker Compose · Linux · Nginx · uWSGI · certbot · GitHub Actions ·
Ruff · mypy · pytest · Uvicorn / Gunicorn при необходимости

# Проект 8. Investment / Portfolio Analytics Platform

## Цель

Финальный большой проект, объединяющий навыки курса. Сервис должен быть
достаточно полезным, чтобы его можно было развивать после окончания
обучения.

## Что должно быть

Backend платформы для ведения инвестиционного портфеля и анализа
результатов.

Сущности: User, Portfolio, Account, Asset, Transaction, Position, Price,
Dividend

API: создание портфеля, добавление сделок, текущие позиции, история
стоимости портфеля, доходность, статистика, импорт котировок, фоновые
обновления данных.

Аналитика: P&L, ROI, CAGR, volatility, Sharpe ratio, Sortino ratio, maximum
drawdown.

Архитектуру сначала реализовать как **modular monolith**, а не сразу как
набор микросервисов.

Модули: auth, portfolio, transactions, market data, analytics,
notifications.

Отдельный ingestion-компонент должен асинхронно получать данные из внешнего
API.

Добавить: Redis cache, background jobs, RabbitMQ, PostgreSQL, raw SQL для
тяжёлой аналитики, ORM для обычных CRUD-операций, idempotency,
audit/logging, metrics, CI/CD, production deployment.

После рабочей версии modular monolith в качестве дополнительного задания
выделить один модуль, например `notification-service`, в отдельный сервис.

## Использовать

FastAPI · aiohttp · PostgreSQL · SQLAlchemy · Raw SQL · Redis · RabbitMQ ·
Celery · Alembic · Docker Compose · Nginx · pytest · GitHub Actions ·
Prometheus · Grafana

## Definition of Done (для каждого проекта)

- функциональность работает;
- есть миграции;
- есть unit/integration tests;
- обработаны ошибки;
- нет очевидных N+1;
- проверены важные SQL-запросы;
- приложение запускается через Docker;
- код проходит lint/type checks;
- README позволяет другому разработчику запустить проект;
- ты можешь объяснить архитектурные решения без подсказки.

## Главный принцип курса

Каждый следующий проект должен не повторять предыдущий CRUD, а добавлять
новую инженерную проблему:

`asyncio → PostgreSQL → Django → concurrency → networking → queues →
production → system design`
